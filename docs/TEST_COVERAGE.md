# Test Coverage

This document maps each acceptance criterion to the Playwright test that checks it, based on what each test actually asserts (not just its name). Line numbers refer to the `test(...)` declaration.

- API tests: `playwright-tests/tests/rbac.spec.ts` (16 tests)
- UI tests: `playwright-tests/tests/rbac-ui.spec.ts` (4 tests), using `playwright-tests/tests/pages/DashboardPage.ts`
- The suite runs in 3 browsers (chromium, firefox, webkit) with `workers: 1`, so 20 tests produce 60 runs.

`DashboardPage` exposes three methods: `goto()`, `login(role)` (picks the role in the combobox and clicks Login), and `getCampaignNames()` (waits for the table, then reads the first cell of every body row). The UI tests can therefore only observe campaign names in the rendered table. They do not read stat cards, use the create form, or log out.

### What the assertions do and do not prove

- Criteria 6 and 7 use `Array.every`, which is also true for an empty array. They do not assert that the result is non-empty, so they would pass if the endpoint returned nothing.
- Criteria 6, 7 and 10 inspect only the pages they request. Criterion 6 and 7 look at the first 20 rows, not the full set.
- Criteria 13 to 15 check for one specific campaign name per client (each name carries a `Date.now()` suffix). They do not check that no other client's seeded campaigns are in the table.
- Criterion 16 depends on the dashboard fetching `/campaigns?limit=100`. If the database holds more than 100 campaigns, the new campaigns land on page 2 and the test fails even though RBAC is correct. This is why `playwright.config.ts` sets `workers: 1` and why both specs delete what they create in `afterAll`. The `afterAll` deletes use the admin role and do not assert the response status.
- Criterion 3 checks the POST response only. It does not read the campaign back, and it does not check that clientB cannot see it.

## Known gaps

The behaviors below have no test. Statements about current behavior come from reading `backend/src/middleware/auth.ts` and `backend/src/routes/campaigns.ts`, not from running them.

### Gaps you asked about

| Behavior | Status |
|-|-|
| Admin `GET /campaigns` returns campaigns for all clients | **No API test.** Criterion 16 shows admin seeing clientA's and clientB's campaigns in the UI, but only through the 100 row page and only for those two clients. Nothing at the API level asserts that admin results span clients or that admin is unfiltered. |
| Admin `DELETE` of any client's campaign | **No test.** Admin DELETE appears in the `afterAll` cleanups (status not asserted) and in the final step of criterion 4, where it is only used to confirm a 404 for an already deleted campaign. No test deletes a live campaign owned by a client as admin and expects 204. |
| Client deleting its own campaign | **Covered.** This is criterion 5 (`rbac.spec.ts:52`). It is not a gap. |
| Invalid `x-user-role` value (for example `x-user-role: bogus`) | **No test.** The middleware only rejects a missing or empty header. Any other string is accepted, and since it is not `admin` it falls through to the client branch, scoped by whatever `x-client-id` says. With no `x-client-id`, a GET filters on `clientId: null` and a POST fails Mongoose validation with 400. Neither outcome is asserted. |

## Triage agent eval

The eval lives in `triage-agent/src/evalSet.ts` (cases) and `triage-agent/src/runEval.ts` (runner). Run it with `npx ts-node src/runEval.ts` from `triage-agent/`. It needs `ANTHROPIC_API_KEY` in `triage-agent/.env`.

**What it measures.** Each of the 24 hand-written failure cases (test name, error message, stack trace, backend log entries) goes through the full LangGraph `runTriage` path using Claude Haiku (`claude-haiku-4-5-20251001`, temperature 0). The result counts as correct only if the predicted `category` equals the case's `expectedCategory`. It is a single exact-match accuracy number, plus a count of how many cases triggered the second-pass reconsideration (confidence below 0.7).

| Expected category | Cases |
|-|-|
| `product_bug` | 7 |
| `flaky_test` | 5 |
| `environment_issue` | 6 |
| `locator_drift` | 6 |
| `not_a_failure` | 0 |

**Current result:** 21/24 correct (87.5%). No case triggered reconsideration, so the confidence gate never fired, including on the misses.

**The 3 misses.** These come from the author's Sep 21 eval run. `runEval.ts` prints mismatches to the console only, so the repository does not store them, and this table was not regenerated by a fresh run. All three had confidence of 0.7 or higher, so none were reconsidered.

| Test case | Expected | Got |
|-|-|-|
| `submitting the create-campaign form once creates exactly one campaign` | `product_bug` | `flaky_test` |
| `success toast appears after creating a campaign` | `flaky_test` | `locator_drift` |
| `confirmation dialog is visible after deleting a campaign` | `locator_drift` | `product_bug` |

The toast case is the one the README calls ambiguous: a toast timeout after a successful 201 write fits a late render, a missing render, or a stale selector, and a text-only log, error and stack trace cannot tell them apart.

**Limits of the measurement.** The cases are hand-built, not sampled from real failures, and `not_a_failure` has no cases, so this is a directional signal and not a benchmark.
